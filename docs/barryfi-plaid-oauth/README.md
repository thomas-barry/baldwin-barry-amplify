# BarryFi Plaid OAuth redirect page

Documents the `/barryfi/plaid-oauth` route and the hosting rewrite change made
alongside it. Work done 2026-08-09; shipped in commit `3bbba3f`.

## Why this exists

BarryFi (a separate application) uses Plaid Link. For some institutions Plaid
performs an OAuth handoff: the bank opens in a browser or popup and, when the
user finishes authenticating, redirects to a pre-registered HTTPS URI. That URI
has to be a real, publicly reachable page on a domain registered in the Plaid
dashboard. This site serves that role.

The page has no logic — Plaid re-initialises Link in the original tab. All it
does is load, identify itself, and tell the user they're done.

## What the page does

| | |
|---|---|
| Path | `/barryfi/plaid-oauth` |
| Document title | `BarryFi` |
| Heading | `BarryFi` |
| Body copy | `You can close this window and return to BarryFi.` |
| Chrome | None — no sidebar, no topbar, no skip link |

It renders bare because it appears in a popup or redirect window, not as part of
site navigation.

### The app-shell opt-out

The root route normally wraps every page in `Sidebar` + `Topbar` + skip link, so
a bare page needs an explicit escape hatch. `__root.tsx` checks the pathname and
returns a plain `<Outlet />` for anything under `/barryfi/`:

```tsx
const isBarePath = (pathname: string) => pathname.startsWith('/barryfi/');
```

Prefix-matching rather than the exact path keeps future BarryFi handoff pages
bare without another edit.

**Known wrinkle:** the bare branch returns `<Outlet />` *outside*
`LoginDialogProvider`. Nothing breaks today because `PlaidOAuth` never calls
`useLoginDialog()`, but a future `/barryfi/*` route that does would hit a missing
provider. Move the bare return inside the provider if that day comes.

### Layout gotcha

`#root` is `display: flex` (see `src/index.css`), so a full-page container
shrink-wraps its content and any horizontal centring silently does nothing. The
page needs an explicit `width: 100%`. `About.module.css` documents the same trap.

## Hosting rewrite change

Separate from the route itself, the Amplify Hosting custom rules were changed so
SPA deep links return **200** instead of **404**.

Before, every route on the site — `/about`, `/photos`, `/blog`, and the new one —
served the correct SPA HTML but with an HTTP **404** status. Browsers rendered
them fine; the status was simply wrong.

| | Source | Target | Status |
|---|---|---|---|
| Before | `/<*>` | `/index.html` | `404-200` |
| After | `</^[^.]+$\|\.(?!(css\|eot\|gif\|html\|ico\|jpg\|jpeg\|js\|json\|map\|png\|svg\|ttf\|txt\|webmanifest\|webp\|woff\|woff2)$)([^.]+$)/>` | `/index.html` | `200` |

**The source pattern had to change too, not just the status.** `404-200` only
fires when the origin actually 404s, so assets fall through untouched. An
unconditional `200` on `/<*>` would rewrite `/assets/index-*.js` to `index.html`
as well and take the whole site down. The regex passes through anything with a
known extension. `eot` and `webmanifest` were added beyond Amplify's stock list
because both appear in `dist/`.

The apex → `www` 302 redirect rule was left untouched.

Applied via `aws amplify update-app --app-id d1dqcbguba2y7s --custom-rules
file://<rules>.json`. It takes effect immediately, with no rebuild. To roll back,
re-apply the old two-rule set from the table above.

## Registering the URI with Plaid

Two things to get right:

1. **Trailing slash.** Hosting 301s `/barryfi/plaid-oauth` →
   `/barryfi/plaid-oauth/`. Register whichever form Plaid's exact-match check
   expects — a mismatch here is the most likely way this breaks.
2. **Use the `www` host.** The apex domain 302s to `www.baldwinbarry.com`.

## Verification

Checked in a real browser (not just curl) because the title is set client-side —
curl proves routing, not rendering.

Production, cold load in a fresh browser context (the case Plaid always exercises):

- `document.title` = `BarryFi`, `h1` = `BarryFi`, body copy exact
- Zero `<nav>` and zero `<main>` elements on the page
- Centred at both 375px and 1280px viewport widths

After the rewrite change:

| Path | Status | Content-Type |
|---|---|---|
| `/`, `/about`, `/photos`, `/blog`, `/barryfi/plaid-oauth` | 200 | `text/html` |
| `/assets/index-*.js` | 200 | `text/javascript` (902 KB — served as itself, not rewritten) |
| `/assets/index-*.css` | 200 | `text/css` (734 KB) |
| `/site.webmanifest`, `/noise.svg`, `/favicon.ico` | 200 | correct types |

The asset rows are the ones that matter — full size and correct content-type
prove the exclusion regex is working. `/photos` was also loaded in a browser to
confirm images still render.

Local checks: `npx tsc --noEmit`, `npm run lint` (max-warnings 0), `npm run build`
all pass.

## Unrelated observations

Noticed while reading the Amplify app config.

- **The console build spec used to say `pnpm run build`**, while the repo's
  `amplify.yml` says `npm run build` and `CLAUDE.md` mandates npm. The repo file
  wins when present, so builds always did use npm — confirmed in job 37's log.
  The stale console copy was only a hazard if `amplify.yml` were ever deleted or
  renamed, at which point the app would have silently built with a package
  manager this repo does not use and has no lockfile for.

  **Fixed 2026-09-09** by pointing the stored spec at the repo file, so the two
  cannot disagree:

  ```
  aws amplify update-app --app-id d1dqcbguba2y7s --build-spec file://amplify.yml
  ```

  Verified afterwards: zero `pnpm` occurrences in the stored spec, structurally
  identical to `amplify.yml`, and — the part worth checking, since `update-app`
  overwrites what you pass it — `customRules`, `customHeaders`,
  `environmentVariables`, platform and repository all survived intact.

- **`customHeaders` caches `**/*.{js,css,png,jpg,gif}` as `immutable` for a
  year.** Correct for hashed bundles, but `/noise.svg` and the favicons are not
  hashed — relevant if one is ever swapped and appears not to update.
